
# План реалізації фронтенду Claims Module

## Вимоги та реалізація

План спирається на Assessment §3.3, §3.7–3.9, Candidate Specification §5, §9–12 та аналіз вимог бекенду. Маршрути звірено з контролерами й публічним OpenAPI. Віджети Angular Material та компактні таблиці забезпечують основні сценарії на ширині від 1280 px. Тексти інтерфейсу англійською відповідають назвам полів і дій у специфікації.

| Етап | Обсяг | Критерій приймання |
| --- | --- | --- |
| 1. Основа й авторизація | Angular 21, Material, standalone lazy routes, Reactive Forms, типізовані HTTP-сервіси, обробка помилок і токен сесії | Handler, supervisor і manager входять через `/api/auth/demo-token` та `/api/auth/me`. Захищене посилання після входу відкриває початкову сторінку. Запити з помилками показують повідомлення та кореляцію, якщо її повернув API. |
| 2. Список | Серверні фільтри за кількома статусами, датою збитку, іменем handler і причиною, пошук, пагінація, SLA | Фільтри передаються до `GET /api/claims`. Після зміни фільтра відкривається перша сторінка, а рядок веде до деталей. |
| 3. FNOL | Пошук і покриття поліса або Unknown Policy, дата й опис збитку, учасники, об’єкти ризику, опційний резерв, огляд і підтвердження попереджень | На першому кроці перевіряються поля збитку. На другому потрібен Claimant. Третій крок виконує `POST /api/claims/validate` перед створенням Draft і показує номер заявки після успіху. |

| 5. Резерви й файли | Signed delta, пороги, Add/Adjust/Reverse, рішення щодо транзакцій, повторне подання, manager override, стан і повтор GL, завантаження та скачування документів | Заявник подає $15,000, інший користувач із достатньою роллю погоджує. Баланс одразу схвалений, статус GL оновлюється окремо. Завантаження показує прогрес, документ і події доступні з картки. |
| 6. Інтеграційна перевірка та Azure | Unit-тести, браузерний сценарій на 1280 px, запуск із локальним SQL Server і Azure, pipeline збірки та деплою | Результати тестів із тестовим API доповнює запуск із реальним API, SQL, Hangfire й Blob. Публічні URL UI і API та Swagger доступні рев’юерам. |

## Архітектура і відповідність API

- Компоненти використовують `ClaimsApi`. Токен зберігається в пам’яті вкладки, а interceptor додає Bearer лише для API. Після перезавантаження потрібен вхід. Роль підтверджує API; видимість дій допомагає користувачу орієнтуватися. Auth/me повертає ідентифікатори й роль, тому сторонні актори відображаються за ідентифікатором.
- Для списку використано повторювані query-параметри `status`, `assignedHandlerName` та пагінацію API, яка починається зі сторінки 1. Інтервал поліса перевіряється за днем UTC. Дата й час збитку вводяться в місцевому часі та передаються як ISO UTC. SLA відображається окремою позначкою.
- Перелік переходів повертає `/api/reference/claim-statuses`. `/closure-check` перевіряє факти конкретної заявки, а команда повторює перевірку під час запису. `Reopened` призводить до остаточного стану Open й окремих подій аудиту. У демо handler бере свій ID з `/auth/me`. Для відкриття непризначеного Draft під supervisor або manager доступний параметр `demoHandlerId`, оскільки API ще не має публічного довідника працівників.
- Reserve Adjust/Reverse адресують компонент за `reserveId`; approve/reject/retract/retry адресують операцію за `txnId`. Пороги застосовуються до абсолютної величини дельти. Точні десяткові значення передаються JSON-числами, відображаються без округлення до двох знаків і обчислюються як цілі одиниці по 0,0001. Правила підсумку, схвалення та менеджерського override остаточно перевіряє API.
- Ключ ідемпотентності діє в межах користувача, маршруту й того самого тіла запиту. Клієнт повторює ключ після невизначеного результату в поточній вкладці. Попередня перевірка FNOL є читанням і не використовує ключ. Структуровані помилки показуються в контексті операції та через snackbar.
- Для upload використовується multipart `file`, `documentType`, `notes`. Azure download відкриває свіжий SAS без Bearer, локальний провайдер повертає файл через авторизований API. У браузері перевіряються розширення та 50 MiB, сервер перевіряє тип і вміст.
- Angular dev server проксіює `/api` до локального HTTPS API. Окремий Azure UI потребує дозволеного origin у CORS API, доступних методів GET/POST/PUT/DELETE, заголовків Authorization, Content-Type та Idempotency-Key і видимого `X-Correlation-ID`. У поточному `Program.cs` CORS middleware відсутній, тому для Azure потрібно налаштувати його на сервері або в App Service та перевірити preflight. У build включено SPA fallback для прямих посилань на заявки. [Конфігурація Azure Static Web Apps](https://learn.microsoft.com/en-us/azure/static-web-apps/configuration)

## Перевірки перед здачею

- Запустити `npm ci`, `npm test -- --watch=false`, `npm run build`, `npm run test:e2e` і `dotnet test ClaimsModule.sln` у відповідних проєктах.
- На тестовому середовищі пройти FNOL → Open → резерв → схвалення іншим акаунтом → GL → вкладення → аудит. Перевірити пороги $10,000 і $100,000, позитивний залишок при Closed, втрату сесії, 422/409, Azure SAS, локальний файл і недопустимий перехід.
- Зібрати UI в pipeline, додати до наявного деплою API та EF міграцій крок деплою UI в Azure Static Web Apps або другий App Service. Перевірити обидва URL та оновити README, архітектуру і фактичну AI-історію перед передачею рев’юерам.
